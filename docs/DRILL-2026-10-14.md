## Findings from the drill, and what we changed

1. **§3.3 baseline was empty for a fix MR into a feature branch** (commit `abee55e`). The gate compared the fix MR's
   findings with the latest *green* pipeline on its target branch; the feature branch had only a failed pipeline
   (container scanning never ran there), so all 8 pre-existing base-image CVEs counted as new. Baseline is now the
   latest green pipeline on the target **and** the default branch. Regression test: `test_baseline_falls_back_to_default_branch`.
2. **A deterministic check could override the reviewer agent** (commit `838637f`). On !2's second pipeline F2 said
   HUMAN REQUIRED (the pipeline was still running when it reviewed); `policy-check` then added the scoped label
   `autopilot::approved`, GitLab dropped F2's `autopilot::needs-human` from the same scope, and auto-merge read the
   label as the reviewer's approval. Harmless here (empty net diff), wrong in principle. Now the newest signed
   reviewer verdict decides §3.2 (a recorded MR approval would also count, but in this project none is recorded:
   see the 401 observation under run 4); the label counts only when no reviewer verdict exists; policy-check no
   longer adds `approved` over a non-APPROVED verdict. Regression test: `test_reviewer_gate_respects_agent_verdict`.
3. **The rollback depended on a permission we do not have** (commit `5f2d251`). `incident.py` started the rollback as
   a pipeline on `main` with the pipeline variable `ROLLBACK_TO=<tag>`. The showcase's "Minimum role to use pipeline
   variables" is above Developer, our role in the hackathon group, and only a Maintainer can change it. So the call
   was refused with 400. Now the release tag and the incident are in a **branch name**: `incident.py` creates
   `rollback/v0.1.2/incident-3` from the commit the monitor ran on, which keeps the current `.gitlab-ci.yml`. It then
   starts a pipeline on that branch with `CI_JOB_TOKEN` and **no variables**. The deploy jobs, `rollback-note` and
   `audit-trail` match the `rollback/v…` prefix. `scripts/rollback_ref.py` turns the branch name back into
   `ROLLBACK_TO` / `INCIDENT_IID`, and `deploy.py` still builds the release tag's commit. The workflow rules skip the
   push pipeline that creating the branch can cause, so exactly one rollback pipeline runs. §6.2 is unchanged:
   automatic, to the last release, never forward. Regression tests: `tests/test_rollback.py`, which includes a replay
   of this incident through `incident.main` and asserts that the trigger carries no variables. **Not yet exercised by
   a live incident.** Caveat for live deployments: a masked *protected* `RENDER_API_KEY` is not exposed on an
   unprotected `rollback/*` branch, so protect `rollback/*` (push: Developers + Maintainers) or leave that key
   unprotected. The showcase's deploys are dry runs, so this does not change the drill.
4. **The "monitor-only" schedule was not monitor-only.** Both scheduled pipelines of the drill (2945603793 and
   2945631275) also ran `gemnasium-python-dependency_scanning` (54.0 s and 47.6 s). The Dependency Scanning
   template's rule matches every branch pipeline and only runs where the Ultimate feature is on. Our schedule
   measurements came from the Free-tier history project, where the job never appeared. Its rule would also have
   matched the `rollback/<tag>/…` branches of finding 3. Now the job runs on MR and main pipelines only. The workflow
   rule for scheduled and rollback pipelines also sets the four `*_DISABLED` switches, so no other template analyzer
   can start there. `docs/SCI.md` §4 is corrected from measured durations: the schedule cost 15.9 runner-minutes a
   day, not the 6.0 we had claimed, and costs 6.4 now. Regression tests: `tests/test_ci_rules.py` evaluates the rules
   for scheduled, rollback, main and MR pipelines.
5. **The rollback target could be the release already running** (F4's RCA said a rollback to `v0.1.2` would not
   change anything). `/version` did not answer, so `incident.py` fell back to "the newest release", `v0.1.2`, the
   showcase's only release, on which production's code was already built. Had the permission error of finding 3 not
   stopped it, the "rollback" would have redeployed the same release. Now the deployed release comes from `/version`
   or, failing that, from production's last successful deployment (Deployments API: a `rollback/<tag>/…` ref, a tag
   ref, or a release's exact commit), and the target is the newest release older than it. When nothing names the
   deployed release, or no older release exists, there is no target: the incident description and a note say a human
   must roll back. Replayed against the drill (only `v0.1.2`, production last deployed by a later `main` commit), the
   result is no target and no rollback pipeline. Regression tests: `tests/test_rollback.py`
   (`test_incident_main_replays_the_drill_without_a_guessed_target` and the `release_of_deployment` cases).

6. **(Run 4) Code Review findings were advisory, and the gate merged past a valid one.** On MR !4 GitLab Duo Code
   Review flagged at 07:37 that the new `uptime 24h` column's value was untested; `auto-merge` merged at 07:39
   because nothing in §3 looked at review threads. New **AUTOPILOT §3.7**: while the MR has an unresolved,
   resolvable discussion thread, `auto-merge` holds it (`autopilot::needs-human`, note cites §3.7 and links each
   thread). Threads by GitLab Duo Code Review (user `GitLabDuo`) are listed first, but any unresolved thread counts.
   `auto-merge` reads `GET /merge_requests/:iid/discussions` and first waits up to 5 minutes for Code Review to post,
   which closes the race where a review lands after the gate. Plain comments (verdicts, policy notes) are not
   resolvable and never hold. It cannot deadlock the Developer flow: resolving the thread (a human, or a follow-up
   commit plus resolve, both allowed to a Developer) releases the hold on the next pipeline or a re-run of
   `auto-merge`. Regression tests: `tests/test_review_threads.py`, against a fixture shaped like the API's output for
   !4. The test gap itself went back to the agents as a follow-up issue: issue #5, run 5 above.

7. **(Run 5) Two of today's fixes interacted: the §3.3 baseline × the scanner-free schedule** (commit `f3b096e`).
   Finding 1 made the baseline the latest *green* pipeline on the target and the default branch; finding 4 made the
   monitor schedule run no scanners. At 08:08 the first schedule run after that change (pipeline 2945847325) became
   the newest green pipeline on `main`, with zero findings, so at 09:18 `auto-merge` held MR !5 with "8 NEW
   High/Critical findings (absent on main)". Against main push pipeline 2945783422 the MR had the same 44 findings,
   none new. Each fix had its own test; no test combined them, the live run did. The baseline now takes the newest
   green pipeline whose source runs the scanners (it skips `schedule`, `trigger`, `pipeline`, `parent_pipeline`,
   `chat`). Regression test: `test_baseline_skips_scanner_free_schedule_pipeline`. MR !5 merged at 09:28 under the
   fixed gate, after a rebase.
8. **(Run 5) A transient registry 500 stopped the MR for 75 minutes** (commit `3c85877`). `build-image` failed at
   07:59:50 with "unexpected status from HEAD request to &lt;registry&gt; 500 Internal Server Error". GitLab
   classified it as `script_failure`, nothing retried it, and the MR waited until a human retried the job at 09:15.
   Now `build-image`, `container_scanning` and `build-wheel` retry GitLab's infrastructure failure classes
   (`retry: max 2` on `runner_system_failure`, `stuck_or_timeout_failure`, `api_failure`, `unknown_failure`,
   `scheduler_failure`, `data_integrity_failure`; never `script_failure`). A registry 5xx inside the script is a
   `script_failure`, which that list cannot match without also retrying real failures, so every `docker login`,
   `build` and `push` in `build-image` also goes through `scripts/registry_retry.sh`: 3 attempts, 10 s backoff
   doubling, retried only when the output matches registry 5xx, "unexpected status", or TLS and network timeouts.
   A broken Dockerfile or a denied push fails at once with its own exit code. `container_scanning` runs the
   template's own script, so it gets only the job-level retry. Regression tests in `tests/test_ci_rules.py` check
   the retry settings and that every docker registry call is wrapped, and replay the run-5 message, timeouts, a
   denied push and a clean success through the wrapper. **Not yet exercised by a live registry error.**

**Observation, F1 woke on the incident** (commit `5f2d251`, with finding 3). The `Work item created` trigger fires for *every* new work
item, incidents included, so T1 started the Planner + Developer flow for Incident #3. Its prompt already said to
skip incidents, but only after the judging-freeze `run_command` step, which means after a full coding environment
had started. F1 changed nothing, but it was a wasted session. The planner's first tool call is now `get_issue`. It
replies SKIP for `issue_type == incident` or the `incident` label before any other call, and AUTOPILOT §1.1 now
says incidents belong to the Incident Responder only. We did **not** drop the `autopilot` label from incidents.
That label is not what wakes F1 (T1 has no label filter), and F4 and the incident re-use lookup search for it. The
registered flow is the copy pasted into AI > Flows, so the new prompt takes effect after it is re-pasted there.
